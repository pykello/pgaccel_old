# Q1 SF100 comparison

All three engines validate every answer in nine consecutive trials.
Eight workers, native storage, a 192 GiB service cap, no swap, and
client-observed query time including fetch and answer conversion.
Warm statistics exclude trial 1. Engines run in separate phases.

| Engine | Warm median (ms) | Warm minimum (ms) |
|---|---:|---:|
| duckdb | 2367.329 | 2304.658 |
| clickhouse | 6659.428 | 6574.094 |
| pgaccel | 427.810 | 423.930 |

PGAccel is **5.53× faster than DuckDB and 15.57× faster than ClickHouse**
on warm medians. Its slowest warm trial (434.799 ms) is also below one
quarter of the fastest DuckDB trial (2304.658 ms). The SF100 gate passes.

## Configuration and boundaries

PGAccel uses the frozen `tpch-work/checkpoints/q1-dense-final-query-runner`
binary with engine changes through `83f9307`, 64 GiB query allocations,
and the same SF100 native snapshot as the original comparison. All eight
tables are loaded; loading is outside the query timer and remains
separately reported in raw metadata. No aggregate or answer cache exists.

DuckDB uses its persistent SF100 database. ClickHouse uses the preserved
`tpch_sf100_mergetree` tables with column statistics on isolated ports
18123/19000. Merges are stopped and layout preparation is outside timing.
Q1 uses original SQL in every engine, without dialect adaptation.

The compact machine-readable evidence is `Q1-SF100.json`. Raw JSONL,
phase commands, resource samples, and logs are in
`/home/hadi/projects/docs/tpch/simd-20260906/`. The original full-workload
[SF100 baseline](../sf100-20260905/RESULTS.md) remains a separate checkpoint.
This result concerns Q1 only and does not claim other queries have these
speedups or that the incomplete baseline is now complete.
